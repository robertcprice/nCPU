================================================================================
SUPPORTED MOG TENSOR OPERATIONS
================================================================================

1. BROADCAST
   Signature: broadcast(scalar: int) -> tensor<N, dtype>
   Example: let t = broadcast(5) as tensor<4, i64>;
   Semantics: Fill all N elements with the scalar value
   Validation: None (any scalar, any shape)

2. DOT PRODUCT
   Signature: dot(a: tensor<N>, b: tensor<N>) -> int
   Example: let d = dot(v1, v2) as i64;
   Semantics: Sum of element-wise products
   Validation: Shapes must match exactly

3. MATRIX MULTIPLICATION
   Signature: matmul(a: tensor<N,M>, b: tensor<M,K>) -> tensor<N,K>
   Example: let c = matmul(a, b) as tensor<3, 4>;
   Semantics: Standard matrix multiplication (N×M · M×K → N×K)
   Validation: Both inputs 2D, a.cols == b.rows

4. TRANSPOSE
   Signature: transpose(a: tensor<N,M>) -> tensor<M,N>
   Example: let at = transpose(a) as tensor<5, 3>;
   Semantics: Swap dimensions (flip rows and columns)
   Validation: Input must be 2D

5. SLICE_ROW
   Signature: slice_row(matrix: tensor<N,M>, idx: int) -> tensor<M>
   Example: let row = slice_row(mat, 2) as tensor<5, i64>;
   Semantics: Extract row idx from matrix
   Validation: Input 2D, 0 <= idx < N

================================================================================
KEY INSIGHTS & DESIGN DECISIONS
================================================================================

1. SHAPE VALIDATION AT CODE GENERATION TIME
   Decision: Validate tensor shapes before emitting Mog
   Rationale: Catch mismatches early (synthesis) not at runtime (execution)
   Tradeoff: Requires storing variable types; enables error reporting with context

2. ZERO-COPY VARIABLE BINDING
   Decision: Variables stored as String names, not owned values
   Rationale: Enables late binding (variables may be function parameters)
   Tradeoff: Requires HashMap lookups; avoids deep cloning of tensor data

3. STATELESS STANDALONE FUNCTIONS + STATEFUL BUILDER
   Decision: Provide both APIs (single-op codegen_* and multi-op TensorCodegen)
   Rationale: Standalone for simple cases, builder for composition
   Tradeoff: Code duplication minimized via builder using standalones internally

4. MOG TYPE ANNOTATIONS MATCH TENSOR SHAPE
   Decision: Emit "tensor<3, 4, i64>" for TensorType { shape: [3, 4], dtype: "i64" }
   Rationale: Type information preserved for transpiler and runtime validation
   Tradeoff: Requires Mog parser update to support new syntax

5. FRESH VARIABLE NAMING (t_0, t_1, ...)
   Decision: Auto-increment counter for deterministic names
   Rationale: Reproducible, collision-free, easy to debug
   Tradeoff: User loses naming flexibility (could add optional custom names in future)
